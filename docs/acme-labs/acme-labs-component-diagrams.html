Acme Labs — component architecture diagrams

One detailed diagram per component of the plan (identity & CI → Terraform stacks → network → egress doors → DNS → firewall → GKE → pod → logging → Flux → mesh → ingress → delivery → stretch labs). Companion to acme-labs-design.html and acme-labs-plan.md.

1Identity & CI — GitLab → GCP federation

Component: platform/bootstrap + platform/ci-templates. No JSON keys anywhere.

Read it: job → JWT → WIF checks → STS mints a short-lived token for the SA the job asks to impersonate. ① the same JWT shape comes from every job; the claims differ.
Trust boundary: lives in the provider's attribute mapping and the SA's workloadIdentityUser principalSet — not in GitLab settings.
Prove it: a feature-branch job asking for pipeline-p must fail at STS; for pipeline-p-ro it works.

2Terraform stacks, state and shared modules

Component: Tier-1 modules reused by Tier-1 stacks and Tier-3 domain infra. One state prefix per stack in the np bucket.

Blast radius: each stack has its own state prefix; domain infra can never destroy the network.
No copy-paste: the three domain repos differ by 3 lines because logic lives in app-identity at a pinned tag.
Handoffs: remote_state for platform outputs; deterministic names between Terraform and Flux.

3VPC, subnets and IPAM

Component: platform/network (part 1). Every CIDR is a decision you have to defend.

Why decide first: pod/service secondary ranges are baked into the cluster; changing them means rebuilding.
Capacity math: max_pods_per_node=64 gives each node a /25; a /20 pod range therefore caps you at 32 nodes.
Hidden: the proxy-only subnet is consumed by Google's Envoys, not your workloads — but your firewall must still allow it.

4Routes and the four outbound doors

Component: platform/network (part 2). Longest prefix wins; priority breaks ties; tags scope who a route applies to.

Key nuance: Cloud NAT is not a route — it only acts on packets already routed to the internet gateway.
Why two static IPs: partners allow-list nat-external-0/1; ephemeral IPs would break them.
Per-pod egress: impossible at VPC level; use NetworkPolicy / Istio REGISTRY_ONLY (S5).

5DNS path for Private Google Access

Component: Cloud DNS private zones + VIP routes. Without both, Door 1 silently fails after the default route is gone.

Verify: from the probe VM, dig storage.googleapis.com must return 199.36.153.x; curl -I https://storage.googleapis.com must connect.
Nuance: the Istio chart repo host istio-release.storage.googleapis.com also resolves through the wildcard — Flux may use Door 1 for it.

6Firewall rules and what each one unblocks

Component: platform/network firewall. VPC defaults: deny all ingress, allow all egress — add only justified ingress.

7GKE cluster internals + Workload Identity path

Component: platform/gke-platform. Private zonal Standard cluster, Dataplane V2, spot nodes.

Two identities: node SA (for the VM, image pulls, node agent) vs per-pod GSA (Workload Identity) — never give app roles to the node SA.
Control-plane access: admin via public endpoint with /32; nodes via peering; Terraform and CI never need the Kubernetes API.

8Anatomy of one application pod

Component: Helm chart acme-microservice + Istio injection. Every domain pod has this shape.

9Central logging pipeline

Component: platform/observability. From every source to one central bucket, with metrics and SQL on top.

10Flux GitOps: controllers, sources and ordering

Component: flux-releases + helm-charts. Which controller talks to which network door.

11Service-to-service request: mesh + policy layers

Component: Istio + NetworkPolicy. One call orders → payments shown hop by hop, with where each guard decides.

12Internal ingress path (Gateway API + proxy-only subnet)

Component: Gateway gke-l7-rilb. Where each hop lives and which rule lets it through.

13Delivery: infra pipeline vs application pipeline

Component: GitLab CI (Tier 3) + Artifact Registry + Flux. Two separate paths — GCP objects vs Kubernetes objects.

14Stretch: Private Services Access + hybrid site

Components S1 (Cloud SQL via PSA) and S2 (Door 4: HA VPN to a simulated on-prem VPC). Run for hours, not days — VPN and Cloud SQL cost real money.
